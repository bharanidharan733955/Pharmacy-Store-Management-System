## 📐 Architecture & Exception Design

```
                     +---------------------------------------+
                     |           java.lang.Throwable         |
                     +---------------------------------------+
                                         |
                                         v
                     +---------------------------------------+
                     |           java.lang.Exception         |
                     +---------------------------------------+
                                /                 \
          (Checked Exceptions) /                   \ (Unchecked Exceptions)
                              v                     v
+-------------------------------+                 +--------------------------------+
|   InsufficientStockException  |                 |  java.lang.RuntimeException    |
+-------------------------------+                 +--------------------------------+
| - medicineId: String          |                                  |
| - medicineName: String        |                                  v
| - requestedQuantity: int      |                 +--------------------------------+
| - availableQuantity: int      |                 |    InvalidQuantityException    |
| - getCause(): Throwable       |                 +--------------------------------+
+-------------------------------+                 | - medicineId: String           |
                ^                                 | - invalidQuantity: int         |
                | wrapped cause                   +--------------------------------+
+-------------------------------+
|     InventorySyncException    |
+-------------------------------+
| - warehouseNode: String       |
| - message: DB timeout 3000ms  |
+-------------------------------+
```

### 1. Checked vs. Unchecked Exception Strategy

| Exception Type | Class | Base Class | Rationale & Recovery Strategy |
|---|---|---|---|
| **Checked** | `InsufficientStockException` | `Exception` | Represents a recoverable business condition (warehouse stock shortage). Callers (e.g. pharmacists, order routing) must actively handle this by reordering, offering substitute medicines, or splitting shipments. |
| **Unchecked** | `InvalidQuantityException` | `RuntimeException` | Represents a programming or input validation fault (e.g. quantity `<= 0` or exceeding legal prescription limits). Callers shouldn't recover at runtime without fixing client input. |
| **Chained Infrastructure** | `InventorySyncException` | `Exception` | Represents a lower-level database/network timeout. Wrapped as the cause inside business exceptions so system diagnostics remain intact without breaking high-level abstractions. |

## 🛠 Key Java Exception Handling Concepts

### 1. Exception Chaining (`Caused by:`)
Lower-level errors (such as database query timeouts or warehouse synchronization failures) are chained into high-level business exceptions via `super(message, cause)`:

```java
// Inside InventoryService.java
InventorySyncException syncCause = new InventorySyncException(
    "Database connection timed out after 3000ms while locking SKU " + medicineId,
    "WAREHOUSE_CLUSTER_NODE_04"
);
throw new InsufficientStockException(
    medicineId, medicineName, requestedQuantity, 0,
    "Failed to reserve stock for SKU due to warehouse sync failure",
    syncCause // Chained root cause
);
```

### 2. Java 7+ Multi-Catch Block
Unified handling for both checked business shortages and unchecked validation failures in a single, clean `catch` clause:

```java
try {
    processor.processOrder(order);
} catch (InsufficientStockException | InvalidQuantityException e) {
    // Multi-catch eliminates boilerplate and provides unified logging / rollback
    logger.error("Order rejected by policy: " + e.getMessage());
    order.setStatus(e instanceof InvalidQuantityException ? OrderStatus.REJECTED : OrderStatus.FAILED);
}
```

### 3. Guaranteed `finally` Audit Trail
Regardless of whether processing succeeds, throws a checked exception, throws an unchecked exception, or suffers an unexpected error, the `finally` block **unconditionally** records an audit record to the `AuditService`:

```java
try {
    // Order validation and stock reservation
    finalStatus = OrderStatus.CONFIRMED;
    return order;
} catch (InsufficientStockException | InvalidQuantityException ex) {
    capturedException = ex;
    finalStatus = (ex instanceof InvalidQuantityException) ? OrderStatus.REJECTED : OrderStatus.FAILED;
    rollbackReservedStock(reservedItems);
    throw ex;
} finally {
    // GUARANTEED AUDIT EXECUTION
    auditService.recordAudit(
        order.getOrderId(),
        "PROCESS_ORDER",
        finalStatus,
        capturedException == null ? "Success" : capturedException.getMessage(),
        capturedException
    );
}
```

## 🤖 Copilot Chat Stack Trace Evaluation

Both real stack traces were submitted to **GitHub Copilot Chat**. Here is the recorded analysis:

### 1. Stack Trace 1 Analysis (`InvalidQuantityException`)
- **Copilot Prompt**: *"I encountered this stack trace while running my pharmacy order processor. Can you explain what went wrong and provide the recommended fix?"*
- **Copilot Explanation**: Pinpointed `OrderProcessor.validateOrder` at line 54, explained that `-12` is non-positive, and recommended validating input before calling `processOrder()`.
- **What Copilot Got Right ✅**:
  1. Identified that `MED-102` had an illegal negative quantity `-12`.
  2. Accurately traced the call frames (`main` -> `processOrder` -> `validateOrder`).
  3. Identified `InvalidQuantityException` as an unchecked runtime exception.
- **What Copilot Got Wrong / Missed ❌**:
  1. **Anti-pattern recommendation**: Advised catching generic `catch (Exception e)`, which swallows unexpected runtime faults.
  2. **Domain ignorance**: Failed to mention statutory maximum batch limits (e.g. 1000 units max for pharmacy compliance).
  3. **Missed Audit Context**: Failed to note that the `finally` audit block recorded the order outcome regardless of the throw.

---

### 2. Stack Trace 2 Analysis (Chained `InsufficientStockException` / `InventorySyncException`)
- **Copilot Prompt**: *"Analyze this Java exception stack trace. What is the real underlying cause, and how should my production system handle this failure?"*
- **Copilot Explanation**: Correctly identified the `Caused by:` clause as a 3000ms database timeout while locking SKU `ERR_SYNC_105`. Recommended adding Spring `@Retryable` and returning HTTP 400.
- **What Copilot Got Right ✅**:
  1. Drilled down to the root cause: database connection timed out after 3000ms at line 42.
  2. Recognized that `InsufficientStockException` wrapped the root cause using exception chaining.
- **What Copilot Got Wrong / Missed ❌**:
  1. **Framework Hallucination**: Recommended Spring `@Retryable` and Spring `application.properties` in a pure Core Java 21 project.
  2. **Wrong HTTP Status Code**: Recommended returning HTTP 400 (Bad Request). A database timeout is an internal infrastructure issue, which requires **HTTP 503 (Service Unavailable)** or **HTTP 500**.
  3. **Missed Partial Rollback**: Did not mention that any items reserved before SKU `ERR_SYNC_105` must be rolled back.

## 🚀 How to Build & Run

### Option 1: Running via Maven
```bash
# Compile and run unit tests
mvn clean test

# Run interactive demo application
mvn exec:java
```

### Option 2: Running directly with Java / javac
```bash
# 1. Compile main application
javac -d bin -sourcepath src/main/java src/main/java/com/pharmacy/order/app/OrderProcessorApp.java

# 2. Run the application
java -cp bin com.pharmacy.order.app.OrderProcessorApp
```
